Autenticación, sesiones, tokens y JWT

Clase 41 · Identificar al usuario, comprobar sus permisos y autenticar peticiones a una API mediante sesiones y tokens.

1. Autenticación y autorización

Aunque están relacionadas, la autenticación y la autorización responden a preguntas diferentes.

Concepto Pregunta que responde Ejemplo
Autenticación ¿Quién eres? Iniciar sesión con correo y contraseña
Autorización ¿Qué puedes hacer? Comprobar si puedes acceder al panel de administración

Primero se identifica al usuario y después se comprueba qué acciones tiene permitidas.

La autenticación confirma la identidad del usuario; la autorización determina sus permisos.

Por ejemplo, dos personas pueden iniciar sesión correctamente, pero tener permisos diferentes:

  • Un usuario normal puede consultar su perfil.
  • Un administrador también puede gestionar otros usuarios.

Estar autenticado no significa tener acceso a todos los recursos de la aplicación.

2. HTTP y la necesidad de identificar al usuario

HTTP funciona mediante peticiones y respuestas independientes: 

Cliente  →  petición  →  Servidor
Cliente  ←  respuesta ←  Servidor

Cuando el navegador realiza una nueva petición, el servidor no recuerda automáticamente quién hizo las peticiones anteriores.

HTTP es un protocolo sin estado: cada petición se procesa de manera independiente.

Imaginemos el siguiente proceso:

  1. El usuario envía su correo y contraseña.
  2. El servidor comprueba que son correctos.
  3. Más tarde, el usuario solicita sus datos privados.

En la tercera operación, el servidor necesita algún mecanismo para reconocer al usuario sin pedirle de nuevo la contraseña.

Dos estrategias habituales son:

  • Autenticación basada en sesiones.
  • Autenticación basada en tokens.

3. Autenticación basada en sesiones

3.1. Funcionamiento general

Después de validar las credenciales, el servidor crea una sesión para el usuario.

Los datos asociados a esa sesión podrían ser: 

{
  sessionId: "abc123",
  userId: 27,
  role: "admin"
}

El servidor almacena esos datos en algún sistema preparado para ello, como la memoria, una base de datos o un almacén de sesiones.

El cliente recibe normalmente solo el identificador: 

abc123

Este identificador suele guardarse en una cookie.

Inicio de sesión

El proceso de inicio de sesión sigue este flujo: 

1. Cliente → correo y contraseña → Servidor
2. Servidor comprueba las credenciales
3. Servidor crea una sesión
4. Servidor → cookie con el ID de sesión → Cliente

Peticiones posteriores

En las siguientes peticiones se utiliza el identificador para recuperar la sesión: 

1. Cliente → petición + cookie → Servidor
2. Servidor busca los datos de la sesión
3. Servidor identifica al usuario
4. Servidor comprueba sus permisos
5. Servidor devuelve la respuesta

En la autenticación por sesiones, el cliente conserva normalmente un identificador y el servidor mantiene los datos asociados a esa sesión.

3.2. La cookie de sesión

El servidor puede enviar el identificador de sesión mediante una cabecera HTTP: 

Set-Cookie: sessionId=abc123; HttpOnly; Secure
Configuración Función
HttpOnly Impide que el código JavaScript del navegador lea la cookie
Secure Hace que la cookie solo se envíe mediante HTTPS

En las peticiones posteriores, el navegador puede enviar automáticamente esa cookie al servidor.

Estas configuraciones mejoran la seguridad, pero no solucionan por sí solas todos los posibles riesgos.

3.3. Cierre de sesión

Para cerrar una sesión, el servidor puede eliminar o invalidar los datos asociados a su identificador: 

sessionId abc123 → sesión eliminada

Aunque el cliente intentara utilizar de nuevo ese identificador, el servidor ya no encontraría una sesión válida.

En un sistema de sesiones, el servidor puede invalidar inmediatamente una sesión concreta.

3.4. Ventajas e inconvenientes de las sesiones

Ventajas Inconvenientes
El servidor mantiene el control sobre las sesiones activas Es necesario almacenar información por cada sesión
Las sesiones pueden invalidarse inmediatamente El almacenamiento consume recursos
El cliente solo necesita conservar un identificador Varios servidores deben coordinar el acceso a las sesiones
Muchos frameworks incluyen sistemas de sesión Una arquitectura distribuida requiere soluciones adicionales

4. Sesiones en sistemas distribuidos

Una aplicación puede estar formada por distintos servicios: 

                 Aplicación
                      │
        ┌─────────────┼─────────────┐
        │             │             │
   Conductores    Pasajeros       Pagos
                                      │
                               Notificaciones

Si cada servicio almacena sus propias sesiones, una sesión creada en uno de ellos no tiene por qué estar disponible en los demás.

Por ejemplo:

  1. El usuario inicia sesión en el servicio de pasajeros.
  2. Ese servicio crea y almacena su sesión.
  3. El usuario intenta realizar un pago.
  4. El servicio de pagos también necesita identificarlo.

Para coordinar las sesiones pueden utilizarse distintas soluciones:

  • Un almacenamiento de sesiones compartido.
  • Un servicio central encargado de gestionarlas.
  • Afinidad de sesión o sticky sessions.
  • Un sistema de autenticación basado en tokens.

Sticky sessions

La afinidad se aplica entre réplicas del mismo servicio; no comparte por sí sola la sesión con otros servicios.

Una sticky session intenta dirigir las peticiones de un usuario al mismo servidor que creó su sesión.

Esto puede simplificar la gestión porque el usuario vuelve al servidor que ya conoce su sesión.

También aumenta la dependencia respecto a ese servidor. Si deja de estar disponible, será necesario recuperar la sesión mediante otro mecanismo.

5. Autenticación basada en tokens

5.1. ¿Qué es un token?

Un token es un valor que el cliente presenta al servidor como credencial. 

Cliente → petición + token → Servidor

Un token es una credencial que el cliente presenta al servidor; JWT es solo uno de los formatos que puede utilizar ese token.

Por tanto, no todos los tokens son JWT. Algunos tokens son identificadores opacos cuyos datos se consultan en el servidor.

5.2. Funcionamiento general

Después de comprobar las credenciales, el servidor genera un token y se lo entrega al cliente. 

1. Cliente → correo y contraseña → Servidor
2. Servidor comprueba las credenciales
3. Servidor genera un token
4. Servidor → token → Cliente

En las peticiones posteriores, el cliente envía ese token: 

1. Cliente → petición + token → Servidor
2. Servidor comprueba el token
3. Servidor identifica al usuario
4. Servidor comprueba sus permisos
5. Servidor devuelve la respuesta

El token se envía frecuentemente mediante la cabecera Authorization: 

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Elemento Significado
Authorization Cabecera utilizada para enviar las credenciales
Bearer Indica que el cliente presenta un token de acceso
eyJ... Valor concreto del token

El cliente debe enviar el token en cada petición que necesite autenticación.

5.3. Autenticación sin estado

Un sistema de tokens puede funcionar sin almacenar en el servidor una sesión individual para cada usuario. 

Petición
   │
   ├── token
   │     ├── identidad
   │     ├── permisos o rol
   │     └── fecha de expiración
   │
   └── el servidor verifica el token

Cada petición lleva la información necesaria para comprobar la identidad del usuario.

En un sistema stateless, el servidor no necesita recuperar una sesión almacenada para identificar cada petición.

Esto no significa que el servidor deje de utilizar bases de datos.

El servidor puede seguir necesitándolas para consultar usuarios, productos, pedidos o cualquier otro dato de la aplicación.

6. ¿Qué es JWT?

JWT significa JSON Web Token.

Es un formato estandarizado y compacto para representar información que puede ser verificada.

Se utiliza con frecuencia en sistemas de autenticación y autorización, especialmente cuando intervienen diferentes servicios.

Un JWT suele tener este aspecto: 

xxxxx.yyyyy.zzzzz

El JWT firmado en formato compacto que estudiamos aquí está formado por tres partes separadas mediante puntos: 

header.payload.signature
Parte Contenido
Header Tipo de token y algoritmo de firma
Payload Información o declaraciones del token
Signature Firma utilizada para comprobar su autenticidad e integridad

6.1. Header

El header o encabezado describe el token y el algoritmo empleado para firmarlo. 

{
  "alg": "HS256",
  "typ": "JWT"
}
Propiedad Significado
alg Algoritmo utilizado para crear la firma
typ Tipo de token

6.2. Payload

El payload contiene información sobre el usuario y sobre el propio token. 

{
  "sub": "27",
  "role": "admin",
  "exp": 1760812800
}

Estos datos reciben el nombre de claims.

Claim Significado
sub Identificador del sujeto al que pertenece el token
role Rol asignado al usuario
exp Momento en el que expira el token

No es necesario introducir todos los datos del usuario. Normalmente se incluye solo la información necesaria.

Nunca deben almacenarse contraseñas ni otros datos sensibles en el payload.

6.3. Signature

La signature es la firma del token.

Para calcularla se utilizan:

  • El header codificado.
  • El payload codificado.
  • Una clave conocida por el sistema que firma el token.

De manera conceptual, la operación sería semejante a esta: 

firma = firmar(header + "." + payload, clave);

Cuando el servidor recibe el token, comprueba su firma.

Si alguien modifica el header o el payload, la firma deja de coincidir.

La firma permite comprobar que el contenido no ha sido modificado y que el token procede de una fuente que conoce la clave adecuada.

7. Codificación, firma y cifrado

Estos tres conceptos no significan lo mismo.

Operación Finalidad
Codificación Representar los datos en otro formato
Firma Comprobar la autenticidad y la integridad
Cifrado Ocultar la información para que no pueda leerse sin la clave necesaria

En un JWT firmado habitual, el header y el payload están codificados, pero no cifrados.

Esto significa que una persona que consiga el token puede decodificar y leer esas partes.

Un JWT firmado normalmente puede leerse, aunque no pueda modificarse sin invalidar la firma.

La herramienta jwt.io permite observar el header y el payload decodificados. Para practicar, utiliza tokens de ejemplo sin acceso a cuentas reales.

El contenido de un JWT no debe considerarse secreto simplemente porque parezca una cadena incomprensible.

8. Crear, decodificar y verificar un JWT

Estas operaciones deben distinguirse claramente:

Operación Qué hace ¿Demuestra que el token es auténtico?
Crear y firmar Genera el JWT y su firma El emisor utiliza su clave para producirlo
Decodificar Permite leer el header y el payload No
Verificar Comprueba la firma y las condiciones del token Sí, si todas las comprobaciones son correctas

Decodificar solo transforma la información para poder leerla.

Decodificar no comprueba quién creó el token ni si ha sido manipulado.

Antes de confiar en un JWT hay que verificarlo, no solo decodificarlo.

La verificación debe utilizar los algoritmos y claves permitidos por la aplicación. También comprueba la expiración y las condiciones requeridas, como el emisor (iss) y el destinatario (aud).

El proceso puede representarse así: 

JWT recibido
     │
     ├── ¿La firma es válida?
     ├── ¿El token ha expirado?
     └── ¿Es válido para esta aplicación?
              │
              ├── Sí → continuar
              └── No → rechazar la petición

9. Autenticación y autorización con JWT

Un JWT puede incluir información como la identidad y el rol del usuario: 

{
  "sub": "27",
  "role": "admin"
}

El token permite identificar al usuario y conocer determinados datos sobre él.

Sin embargo, el servidor todavía debe decidir si ese usuario tiene permiso para realizar la acción solicitada.

Por ejemplo:

  1. El servidor verifica el JWT.
  2. Obtiene el identificador y el rol del usuario.
  3. Comprueba si ese rol permite eliminar usuarios.
  4. Autoriza o rechaza la operación.

Presentar un JWT válido no garantiza que la operación esté permitida.

10. JWT en una arquitectura de microservicios

En una aplicación distribuida puede existir un servicio central de autenticación: 

Usuario
   │
   └── inicia sesión
             │
             ▼
   Servicio de autenticación
             │
             └── genera JWT
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   Conductores      Pasajeros       Pagos

El usuario puede presentar el mismo token ante distintos servicios si ha sido emitido para que esos servicios lo acepten.

Cada servicio debe:

  1. Recibir el token.
  2. Verificarlo.
  3. Extraer la identidad y la información necesaria.
  4. Comprobar si la operación está autorizada.

De esta forma, los servicios no necesitan compartir una sesión individual para identificar al usuario.

El servicio de autenticación genera el token, pero cada servicio protege sus propios recursos y comprueba los permisos necesarios.

11. Sesiones frente a JWT

Aspecto Sesiones JWT
Estado Los datos de la sesión se guardan en el servidor La información necesaria viaja en el token
Datos del cliente Normalmente un ID de sesión El propio token
Envío habitual Cookie Cabecera Authorization
Invalidación El servidor puede eliminar la sesión El token puede continuar siendo válido hasta expirar
Sistemas distribuidos Requieren coordinar o compartir las sesiones Varios servicios pueden verificar el token
Cambio de datos El servidor puede actualizar la sesión El token conserva su contenido original
Recursos Requieren almacenar sesiones activas Pueden evitar el almacenamiento individual de sesiones

La cookie y la cabecera son mecanismos de transporte: un JWT también puede enviarse en una cookie. La tabla compara configuraciones habituales.

Ningún sistema es siempre superior: la elección depende de las necesidades y de la arquitectura de la aplicación.

11.1. Escalabilidad

Cuando se utilizan sesiones, todos los servidores que atienden al usuario deben poder acceder a los datos de su sesión.

Esto puede requerir:

  • Un almacenamiento compartido.
  • Coordinación entre servidores.
  • Afinidad de sesión o sticky sessions.

Con JWT, diferentes servicios pueden verificar el token recibido sin consultar una sesión central en cada petición.

Utilizar JWT no convierte automáticamente una aplicación en escalable. El resto de la arquitectura también debe estar preparado.

11.2. Invalidación y cierre de sesión

Con sesiones, cerrar sesión puede eliminar los datos almacenados en el servidor: 

ID de sesión → invalidado

Con JWT, el cliente puede eliminar su copia del token y dejar de enviarlo.

Sin embargo, si alguien hubiera robado otra copia, podría seguir utilizándola mientras el token continuara siendo válido.

Eliminar un JWT del cliente no invalida automáticamente todas las copias existentes.

Por eso, los tokens suelen tener una fecha de expiración y, cuando es necesario, se acompañan de mecanismos adicionales de revocación.

11.3. Datos desactualizados

Supongamos que un JWT contiene este rol: 

{
  "sub": "27",
  "role": "admin"
}

Después de emitirlo, el usuario deja de ser administrador.

El token existente continúa conteniendo: 

"role": "admin"

Los cambios realizados en el servidor no modifican automáticamente los tokens que ya fueron emitidos.

Para reducir este problema pueden utilizarse tokens de corta duración o volver a consultar información crítica antes de autorizar determinadas operaciones.

12. Seguridad de sesiones y tokens

12.1. Seguridad de las sesiones

Una implementación con sesiones debe proteger:

  • El identificador de sesión.
  • La cookie que lo transporta.
  • Los datos almacenados en el servidor.
  • El proceso de cierre de sesión.

Las opciones HttpOnly, Secure y el uso de HTTPS ayudan a proteger la cookie y su transmisión.

12.2. Seguridad de los JWT

Un token válido funciona como una credencial.

Si otra persona lo obtiene, podría intentar utilizarlo mientras siga siendo aceptado.

Quien posee un bearer token puede presentarlo ante el servidor como credencial.

Para reducir los riesgos es necesario:

  • Utilizar HTTPS.
  • Definir una fecha de expiración.
  • No incluir información sensible.
  • Verificar la firma.
  • Proteger las claves utilizadas para firmar.
  • Guardar el token cuidadosamente en el cliente.

La firma impide modificar el contenido sin ser detectado, pero no evita que el token pueda ser robado.

13. Ejemplo de petición con un token

Una petición autenticada podría realizarse así: 

fetch("https://api.ejemplo.com/perfil", {
  headers: {
    Authorization: `Bearer ${token}`
  }
});

La plantilla literal introduce el contenido de la variable token después de la palabra Bearer.

El servidor seguirá un proceso semejante a este:

  1. Recibe la petición.
  2. Extrae el token de Authorization.
  3. Verifica el token.
  4. Identifica al usuario.
  5. Comprueba sus permisos.
  6. Devuelve o rechaza el recurso.

Si todo es correcto, podría responder: 

{
  "id": 27,
  "nombre": "Lucía"
}

Si faltan credenciales válidas, podría devolver: 

401 Unauthorized

Si el usuario está identificado, pero no tiene permiso, podría devolver: 

403 Forbidden
Código Significado habitual
401 Unauthorized No se han proporcionado credenciales válidas
403 Forbidden Las credenciales son válidas, pero no permiten realizar la acción

A pesar de su nombre, el código 401 Unauthorized suele indicar un problema de autenticación. El código 403 Forbidden suele indicar un problema de autorización.

14. Flujo completo con JWT

El proceso completo puede representarse así: 

1. El usuario envía sus credenciales
                    │
                    ▼
2. El servidor comprueba su identidad
                    │
                    ▼
3. El servidor genera y firma un JWT
                    │
                    ▼
4. El cliente recibe y conserva el token
                    │
                    ▼
5. El cliente lo envía en otra petición
                    │
                    ▼
6. El servidor verifica el token
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Válido              No válido
          │                   │
7. Comprueba permisos      Rechaza la petición
          │
8. Devuelve el recurso

15. Ideas esenciales

Autenticar consiste en comprobar quién es el usuario.

Autorizar consiste en decidir qué puede hacer ese usuario.

HTTP no recuerda automáticamente las peticiones anteriores.

En un sistema de sesiones, el cliente suele guardar un identificador y el servidor mantiene los datos asociados.

En un sistema basado en tokens, el cliente presenta el token en cada petición protegida.

Token y JWT no son sinónimos: JWT es un formato concreto de token.

Un JWT firmado en formato compacto está compuesto por header, payload y signature.

El contenido de un JWT firmado está codificado, pero no necesariamente cifrado.

La firma permite comprobar la autenticidad y la integridad, pero no oculta los datos.

Decodificar un token no significa verificarlo.

Un JWT válido identifica al usuario, pero el servidor todavía debe comprobar sus permisos.

Las sesiones permiten una invalidación directa; los JWT facilitan el trabajo entre servicios, pero requieren controlar cuidadosamente su expiración y posible revocación.
