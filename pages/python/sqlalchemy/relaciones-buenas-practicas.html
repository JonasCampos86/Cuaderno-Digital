Relaciones y buenas prácticas

Relaciones entre modelos, cascadas, dinero, responsabilidades y carga de datos.

1. Clave foránea y relación ORM

Los fragmentos continúan la configuración de las lecciones anteriores: se reutilizan Base, engine, SessionLocal y los modelos según corresponda.

Una clave foránea conecta filas de dos tablas. Una relación ORM permite navegar entre los objetos que representan esas filas.

Clave foránea:

pedido_id: Mapped[int] = mapped_column(
    ForeignKey("pedidos.id"),
    nullable=False,
)

Relación ORM:

pedido: Mapped["Pedido"] = relationship(
    back_populates="lineas",
)

ForeignKey protege la relación en la base de datos. relationship() facilita trabajar con ella desde Python.

2. Relación uno a muchos

Un pedido puede tener muchas líneas, pero cada línea pertenece a un solo pedido.

Pedido 1 ───── N PedidoProducto

La clave foránea está en el lado muchos:

pedido_producto.pedido_id → pedidos.id

3. back_populates

Este fragmento muestra solo los atributos de relación; los modelos completos, con sus tablas y claves, aparecen en el apartado 5.

back_populates conecta explícitamente los dos extremos de una relación bidireccional.

class Pedido(Base):
    lineas: Mapped[list["PedidoProducto"]] = relationship(
        back_populates="pedido"
    )


class PedidoProducto(Base):
    pedido: Mapped["Pedido"] = relationship(
        back_populates="lineas"
    )

Permite navegar en ambas direcciones:

pedido.lineas
linea.pedido

Los nombres indicados en back_populates deben coincidir exactamente con los atributos del otro modelo.

4. Relación muchos a muchos

Un pedido puede contener varios productos y un producto puede aparecer en varios pedidos.

Pedido N ───── N Producto

Esta relación necesita una tabla intermedia.

Tabla intermedia simple

Se utiliza cuando la relación solo necesita almacenar las dos claves foráneas.

Modelo intermedio

Se utiliza cuando la relación contiene datos propios, como la cantidad.

Pedido 1 ───── N PedidoProducto N ───── 1 Producto

PedidoProducto representa una línea de pedido, no solamente una unión técnica.

Técnicamente, el muchos a muchos se construye mediante dos relaciones uno a muchos: Pedido → PedidoProducto y Producto → PedidoProducto.

ColumnaFunción
idIdentifica la línea
pedido_idRelaciona la línea con el pedido
producto_idRelaciona la línea con el producto
cantidadDato propio de la relación

5. Modelos de ejemplo

Producto:

from decimal import Decimal
from sqlalchemy import Numeric, String
from sqlalchemy.orm import Mapped, mapped_column, relationship


class Producto(Base):
    __tablename__ = "productos"

    id: Mapped[int] = mapped_column(primary_key=True)
    nombre: Mapped[str] = mapped_column(
        String(255),
        nullable=False,
    )
    precio: Mapped[Decimal] = mapped_column(
        Numeric(10, 2),
        nullable=False,
    )

    lineas: Mapped[list["PedidoProducto"]] = relationship(
        back_populates="producto"
    )

Pedido:

from decimal import Decimal
from sqlalchemy import Numeric, String


class Pedido(Base):
    __tablename__ = "pedidos"

    id: Mapped[int] = mapped_column(primary_key=True)
    cliente: Mapped[str] = mapped_column(
        String(255),
        nullable=False,
    )
    total: Mapped[Decimal] = mapped_column(
        Numeric(10, 2),
        default=Decimal("0.00"),
        nullable=False,
    )

    lineas: Mapped[list["PedidoProducto"]] = relationship(
        back_populates="pedido",
        cascade="all, delete-orphan",
    )

Línea de pedido:

from sqlalchemy import ForeignKey


class PedidoProducto(Base):
    __tablename__ = "pedido_producto"

    id: Mapped[int] = mapped_column(primary_key=True)
    pedido_id: Mapped[int] = mapped_column(
        ForeignKey("pedidos.id"),
        nullable=False,
    )
    producto_id: Mapped[int] = mapped_column(
        ForeignKey("productos.id"),
        nullable=False,
    )
    cantidad: Mapped[int] = mapped_column(
        default=1,
        nullable=False,
    )

    pedido: Mapped["Pedido"] = relationship(
        back_populates="lineas"
    )
    producto: Mapped["Producto"] = relationship(
        back_populates="lineas"
    )

6. Cascadas

Una cascada indica cómo debe comportarse SQLAlchemy con los objetos relacionados.

lineas = relationship(
    back_populates="pedido",
    cascade="all, delete-orphan",
)

delete-orphan permite eliminar una línea cuando deja de pertenecer a su pedido.

Esta cascada la gestiona el ORM. No configura por sí sola un ON DELETE CASCADE en MySQL.

Las cascadas deben decidirse según las reglas reales. No deben añadirse automáticamente a todas las relaciones.

7. Crear objetos relacionados

Es preferible expresar la relación mediante objetos:

from decimal import Decimal

producto = Producto(
    nombre="Pizza margarita",
    precio=Decimal("8.50"),
)

pedido = Pedido(cliente="Ana Martínez")
pedido.lineas.append(
    PedidoProducto(
        producto=producto,
        cantidad=2,
    )
)

with SessionLocal.begin() as session:
    session.add(pedido)

SQLAlchemy utiliza las relaciones y claves foráneas para ordenar los INSERT necesarios.

Este ejemplo guarda el pedido y sus líneas, pero no calcula su total: la columna conserva el valor predeterminado 0.00. El apartado 9 explica el cálculo; asignarlo y guardarlo requiere una decisión explícita de la aplicación.

8. Dinero y Decimal

Debe evitarse Float para almacenar dinero porque la coma flotante puede introducir errores de precisión.

Modelo:

precio: Mapped[Decimal] = mapped_column(
    Numeric(10, 2),
    nullable=False,
)

Creación correcta:

precio=Decimal("8.50")

Los valores Decimal deben construirse preferiblemente desde texto. Si se crean desde un float, pueden heredar su imprecisión.

En Python se utiliza Decimal y en MySQL DECIMAL mediante Numeric.

9. Información calculada

Un total puede calcularse a partir del precio y la cantidad:

from decimal import Decimal


def calcular_total(pedido: Pedido) -> Decimal:
    return sum(
        (
            linea.producto.precio * linea.cantidad
            for linea in pedido.lineas
        ),
        start=Decimal("0.00"),
    )

Si el total también se almacena en una columna, puede quedar desactualizado cuando cambian precios o cantidades.

Debe decidirse:

  • Cuándo se calcula.
  • Cuándo se guarda.
  • Si debe conservar el precio histórico de cada operación.
  • Qué ocurre cuando cambia el precio actual del producto.

10. Orden de importación y create_all()

SQLAlchemy solo puede crear las tablas registradas en Base.metadata.

Orden correcto:

from database import Base, engine
from models import Pedido, PedidoProducto, Producto

Base.metadata.create_all(bind=engine)

Si create_all() se ejecuta antes de importar los modelos, algunas tablas no se crearán.

También debe evitarse que cada archivo cree tablas automáticamente al ser importado.

11. Separación de responsabilidades

En una organización básica pueden separarse:

ElementoResponsabilidad
ModeloMapea datos y relaciones
RepositorioConsulta y guarda objetos
ServicioAplica reglas de negocio
PresentaciónMuestra resultados o recibe datos
InformeGenera documentos

La finalidad no es crear muchas clases, sino evitar que una sola parte consulte, valide, calcule y presente todo a la vez.

12. SOLID aplicado de forma breve

Responsabilidad única

Cada componente debe tener un motivo principal para cambiar.

Abierto/cerrado

Una regla puede ampliarse mediante nuevas implementaciones sin modificar continuamente el código existente.

Sustitución de Liskov

Una implementación debe poder sustituir a su abstracción respetando el comportamiento esperado.

Segregación de interfaces

Las capacidades independientes deben separarse para que una clase no dependa de métodos que no utiliza.

Inversión de dependencias

La lógica de negocio no debería depender directamente de una sesión global o de una implementación concreta.

Estos principios no se cumplen únicamente por crear herencia o clases abstractas. Deben mejorar realmente las dependencias y responsabilidades.

13. Control de la transacción

El repositorio puede añadir o consultar objetos, pero una operación superior debe controlar la transacción completa.

Ejemplo:

with SessionLocal.begin() as session:
    repositorio = RepositorioPedidos(session)
    servicio = ServicioPedidos(repositorio)

    servicio.crear_pedido(datos)

Si la operación crea un pedido, varias líneas y actualiza existencias, todo puede confirmarse o revertirse conjuntamente.

Una operación de negocio completa suele necesitar una sola transacción coherente.

14. Carga de relaciones y problema N+1

Al acceder a una relación, SQLAlchemy puede ejecutar una consulta adicional.

Ejemplo:

pedidos = session.scalars(select(Pedido)).all()

for pedido in pedidos:
    for linea in pedido.lineas:
        print(linea.producto.nombre)

Si se ejecuta una consulta inicial y después otra por cada pedido o producto, aparece el problema N+1.

Carga anticipada (con select importado desde sqlalchemy):

from sqlalchemy.orm import selectinload

sentencia = (
    select(Pedido)
    .options(
        selectinload(Pedido.lineas)
        .selectinload(PedidoProducto.producto)
    )
)

pedidos = session.scalars(sentencia).all()

No es necesario anticipar todas las relaciones siempre. Debe elegirse según los datos que vaya a utilizar la operación.

15. Errores frecuentes

Confundir ForeignKey con relationship().

Ejecutar create_all() antes de importar los modelos.

Abrir sesiones en varias funciones y no cerrarlas.

Utilizar Float para dinero.

Depender del orden accidental de las importaciones.

Almacenar datos calculados sin controlar cuándo se actualizan.

Generar una consulta adicional por cada objeto relacionado.

Mezclar consultas, reglas de negocio y presentación en una sola función.

16. Resumen

ForeignKey define la relación en la base de datos.

relationship() permite navegar entre objetos.

back_populates conecta los dos extremos de la relación.

Una relación muchos a muchos con datos adicionales necesita un modelo intermedio.

Decimal y Numeric son apropiados para dinero.

Los modelos deben importarse antes de crear las tablas.

La transacción debe abarcar la operación completa.

SOLID ayuda a separar persistencia y lógica de negocio, pero no exige dividir el código sin necesidad.

El ORM facilita las relaciones, pero el diseño de la base de datos y la calidad del SQL generado siguen siendo responsabilidad del desarrollador.
