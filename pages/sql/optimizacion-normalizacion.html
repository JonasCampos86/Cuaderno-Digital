Optimización y normalización en MySQL

Elegir índices, comprobar cómo se ejecutan las consultas y organizar los datos para reducir redundancia y anomalías.

1. Índices en bases de datos

Un índice es una estructura auxiliar que ayuda a MySQL a localizar determinadas filas sin tener que recorrer necesariamente toda la tabla.

Se parece al índice de un libro: permite llegar directamente a una parte concreta sin leer todas las páginas anteriores.

Los índices pueden acelerar las consultas, pero eso no significa que MySQL vaya a utilizarlos siempre. El optimizador decide si usar un índice o recorrer la tabla completa.

Ventajas de los índices

  • Aceleran muchas búsquedas realizadas con WHERE.
  • Pueden mejorar relaciones mediante JOIN.
  • Pueden ayudar con determinadas ordenaciones y agrupaciones.
  • Permiten localizar valores concretos o rangos de valores.

Costes de los índices

  • Ocupan espacio adicional.
  • Deben actualizarse al insertar, modificar o eliminar datos.
  • Un exceso de índices puede perjudicar el rendimiento de las escrituras.

Un índice debe crearse porque mejora consultas reales, no simplemente porque sea posible crearlo.

2. Una aclaración mínima: InnoDB

InnoDB es el motor de almacenamiento que MySQL utiliza normalmente para gestionar las tablas.

No es una tabla interna ni una tabla adicional. La tabla sigue siendo, por ejemplo, usuarios; InnoDB determina cómo se almacenan sus datos y cómo funcionan sus índices, claves foráneas y transacciones.

Si creamos esta tabla sin indicar ningún motor: 

CREATE TABLE usuarios (
    id INT PRIMARY KEY,
    nombre VARCHAR(50)
);

Si el motor predeterminado es InnoDB, la definición anterior equivale a indicar explícitamente: 

CREATE TABLE usuarios (
    id INT PRIMARY KEY,
    nombre VARCHAR(50)
) ENGINE = InnoDB;

Para trabajar con SQL no necesitamos escribir ENGINE = InnoDB cada vez, pero conocerlo permite entender qué tipos de índice podemos utilizar.

Estas dos definiciones son alternativas. Los ejemplos posteriores de índices presuponen tablas con las columnas indicadas, como email, edad y contenido; no son una continuación de esta tabla mínima.

3. Índices B-Tree

B-Tree es el tipo de índice habitual en MySQL cuando trabajamos con tablas InnoDB.

Puede utilizarse con búsquedas por:

  • Igualdad: =.
  • Comparación: >, <, >=, <=.
  • Rangos: BETWEEN.
  • Listas de valores: IN.
  • Determinadas ordenaciones mediante ORDER BY.

Creación de un índice sencillo: 

CREATE INDEX idx_usuarios_email
ON usuarios(email);

Consulta que podría aprovecharlo: 

SELECT *
FROM usuarios
WHERE email = 'ana@example.com';

Un índice B-Tree también sirve para búsquedas de igualdad. No necesitamos un índice HASH para realizar una consulta con =.

4. Índices compuestos

Un índice compuesto incluye varias columnas. 

CREATE INDEX idx_usuarios_edad_nombre
ON usuarios(edad, nombre);

El orden de las columnas es importante. Este índice está organizado primero por edad y después por nombre.

Regla del prefijo izquierdo

Este índice puede ayudar normalmente en consultas que utilicen su primera columna: 

SELECT *
FROM usuarios
WHERE edad = 25;

También puede ayudar cuando filtramos por las dos columnas: 

SELECT *
FROM usuarios
WHERE edad = 25
  AND nombre = 'Ana';

Además, puede ayudar a filtrar y ordenar cuando la primera columna mantiene un único valor: 

SELECT *
FROM usuarios
WHERE edad = 25
ORDER BY nombre;

En cambio, normalmente no está preparado para buscar únicamente por la segunda columna: 

SELECT *
FROM usuarios
WHERE nombre = 'Ana';

La regla se refiere al orden de las columnas en la definición del índice, no al orden de las condiciones dentro de WHERE. Intercambiar las condiciones unidas por AND no cambia este principio.

Para una búsqueda por prefijo se utiliza la primera columna, o varias columnas consecutivas desde la izquierda. No significa que el índice sea inútil en cualquier otro caso: MySQL puede elegir otras estrategias, que debemos comprobar con EXPLAIN.

5. Rangos dentro de un índice compuesto

SELECT *
FROM usuarios
WHERE edad BETWEEN 18 AND 30
ORDER BY nombre;

El índice (edad, nombre) puede ayudar a localizar el rango de edades.

Sin embargo, no debemos afirmar que también evita necesariamente la ordenación por nombre.

Los datos del índice están ordenados así: 

edad → nombre

Por tanto, los nombres están ordenados dentro de cada edad, pero no globalmente entre todas las edades comprendidas entre 18 y 30.

Un rango puede limitar cómo se usan las columnas posteriores para acotar la búsqueda o resolver la ordenación. Esas columnas todavía pueden ayudar a filtrar; el plan de ejecución determina su uso real.

6. Índices HASH

Un índice HASH está pensado principalmente para comparaciones exactas.

Ejemplo de comparación exacta: 

WHERE email = 'ana@example.com'

No sirve para búsquedas por rango ni para ordenar los resultados.

Además, no está disponible como índice normal creado por el usuario en las tablas habituales InnoDB.

En MySQL se utiliza con motores específicos, como MEMORY. NDB también admite índices HASH, con sus propias restricciones.

Ejemplo de índice HASH si usuarios_temporales utiliza el motor MEMORY: 

CREATE INDEX idx_usuarios_email
USING HASH
ON usuarios_temporales(email);

Para obtener un índice HASH real, el motor debe admitirlo. En InnoDB, solicitar USING HASH puede generar un aviso y crear el índice B-Tree predeterminado. Que la sentencia termine no demuestra que se haya creado un HASH.

En las tablas InnoDB habituales utilizaremos un índice B-Tree, incluso para búsquedas mediante igualdad.

7. Índices FULLTEXT

Los índices FULLTEXT se utilizan para buscar palabras dentro de textos extensos.

Se pueden crear sobre columnas:

  • CHAR.
  • VARCHAR.
  • TEXT.

Creación del índice: 

CREATE FULLTEXT INDEX idx_posts_contenido
ON posts(contenido);

Búsqueda en modo booleano: 

SELECT *
FROM posts
WHERE MATCH(contenido)
      AGAINST('+receta +pasta' IN BOOLEAN MODE);

En este ejemplo:

  • MATCH(contenido) indica la columna en la que se busca.
  • AGAINST(...) contiene las palabras buscadas.
  • IN BOOLEAN MODE permite utilizar operadores especiales.
  • El signo + indica que la palabra debe aparecer.

La búsqueda siguiente exige que aparezcan las dos palabras: 

+receta +pasta

En InnoDB, las columnas indicadas en MATCH() deben coincidir con las de un índice FULLTEXT. En este ejemplo, el índice y la búsqueda utilizan únicamente contenido.

La búsqueda también depende de las palabras excluidas y de las reglas de tokenización, como la longitud mínima de las palabras.

FULLTEXT está diseñado para buscar palabras dentro de textos; no sustituye a LIKE en absolutamente todos los casos.

8. Elección básica del índice

Necesidad Índice habitual
Igualdad con = B-Tree en InnoDB
Comparaciones y rangos B-Tree
BETWEEN o IN B-Tree
Determinadas ordenaciones B-Tree
Búsqueda dentro de textos FULLTEXT
Igualdad exacta en tablas compatibles Puede utilizarse HASH

No elegimos un índice únicamente por el operador de la consulta. También debemos considerar:

  • El motor de almacenamiento.
  • Las columnas utilizadas.
  • El orden de las columnas.
  • La cantidad y distribución de los datos.
  • Las consultas que realmente ejecutará la aplicación.

9. Consultar y eliminar índices

Mostrar los índices de una tabla: 

SHOW INDEX FROM usuarios;

Eliminar un índice: 

DROP INDEX idx_usuarios_email
ON usuarios;

Eliminar un índice puede empeorar las consultas que dependían de él. Debemos comprobar su uso antes de borrarlo.

10. Comprobar si un índice se utiliza

No debemos considerar optimizada una consulta simplemente porque hayamos creado un índice.

Podemos consultar el plan de ejecución con: 

EXPLAIN
SELECT *
FROM usuarios
WHERE email = 'ana@example.com';

EXPLAIN permite comprobar, entre otras cosas:

  • Si MySQL utiliza un índice.
  • Qué índice ha elegido.
  • Cómo piensa acceder a los datos.
  • Una estimación de las filas que tendrá que revisar.

Crear el índice es una posibilidad de optimización; comprobar el plan con EXPLAIN permite saber qué ha decidido MySQL.

El plan describe la estrategia prevista y sus estimaciones. Por sí solo no demuestra cuánto tiempo tarda la consulta ni cuánto ha mejorado.

11. Normalización de bases de datos

La normalización es un proceso para organizar los datos de una base de datos relacional.

Sus objetivos principales son:

  • Reducir información repetida.
  • Mantener relaciones lógicas entre los datos.
  • Mejorar la consistencia.
  • Evitar determinados problemas al insertar, modificar o eliminar registros.

La normalización no garantiza que todas las consultas sean más rápidas. Una estructura normalizada puede necesitar más tablas y más JOIN.

La normalización busca principalmente mejorar la organización y la integridad de los datos, no sustituir la optimización de consultas.

12. Anomalías en los datos

Anomalía de inserción

Aparece cuando no podemos guardar un dato sin repetir o añadir otra información innecesaria.

Anomalía de actualización

Aparece cuando el mismo dato está repetido y debemos modificarlo en varios registros.

Si el nombre de una ciudad aparece en cien filas, tendríamos que corregirlo cien veces.

Anomalía de eliminación

Aparece cuando al eliminar un registro perdemos también información que queríamos conservar.

13. Primera Forma Normal — 1FN

Una tabla cumple la primera forma normal cuando cada celda contiene un único valor y no existen grupos repetitivos dentro de una misma columna.

Tabla que incumple 1FN

AlumnoID Nombre Cursos
1 Ana Pérez Matemáticas, Física, Química

La columna Cursos contiene varios valores en una sola celda.

Tabla que cumple 1FN

AlumnoID Nombre Curso
1 Ana Pérez Matemáticas
1 Ana Pérez Física
1 Ana Pérez Química

Ahora cada celda contiene un único valor.

Una posible clave sería: 

(AlumnoID, Curso)

Cumplir 1FN no significa que la tabla esté completamente normalizada. Todavía puede contener información repetida que se corregirá en formas normales posteriores.

14. Segunda Forma Normal — 2FN

Una tabla cumple 2FN cuando:

  • Ya cumple 1FN.
  • Sus atributos no clave dependen de cada clave candidata completa, no de una parte de ella.

Una clave candidata es un conjunto mínimo de columnas que identifica una fila; una de ellas se elige como clave primaria. Aquí llamamos no clave a los atributos que no forman parte de ninguna clave candidata.

Las dependencias parciales aparecen cuando existe alguna clave candidata compuesta, aunque no sea la elegida como primaria.

Tabla original

PedidoID ProductoID NombreProducto Cantidad Cliente
1001 501 Laptop 2 Juan Pérez

En este ejemplo, cada pedido tiene un cliente y cada producto aparece una sola vez por pedido. La clave compuesta sería: 

(PedidoID, ProductoID)

Sin embargo, existen dependencias parciales:

  • Cliente depende solamente de PedidoID.
  • NombreProducto depende solamente de ProductoID.
  • Cantidad depende de la combinación (PedidoID, ProductoID).

Separación correcta

Pedidos

PedidoID Cliente
1001 Juan Pérez

Productos

ProductoID NombreProducto
501 Laptop

DetallePedido

PedidoID ProductoID Cantidad
1001 501 2

En 2FN eliminamos dependencias respecto a una parte de una clave compuesta.

15. Tercera Forma Normal — 3FN

Una tabla cumple 3FN cuando:

  • Ya cumple 2FN.
  • Los atributos no clave dependen directamente de la clave.
  • No existen dependencias transitivas entre atributos no clave.

Tabla original

EmpleadoID Nombre Departamento CiudadSede
101 Carlos R. Ventas Guadalajara

La relación sería: 

EmpleadoID → Departamento → CiudadSede

CiudadSede no depende directamente del empleado, sino del departamento.

Separación correcta

Empleados

EmpleadoID Nombre DepartamentoID
101 Carlos R. 1

Departamentos

DepartamentoID Nombre CiudadSede
1 Ventas Guadalajara

En este ejemplo, separar la sede del departamento evita repetirla en cada empleado y elimina la dependencia transitiva que incumple 3FN.

Esta separación es correcta si cada departamento tiene una única sede. La normalización siempre depende de las reglas reales del negocio.

16. Resumen final

Índices

  • B-Tree es el índice normal en InnoDB.
  • Sirve para igualdad, comparaciones y rangos.
  • En los índices compuestos importa el orden de las columnas.
  • HASH solo está disponible en determinados motores.
  • FULLTEXT permite buscar palabras dentro de textos.
  • Los índices aceleran determinadas lecturas, pero encarecen las escrituras.
  • EXPLAIN permite comprobar si MySQL utiliza realmente un índice.

Normalización

  • 1FN: valores atómicos y sin listas dentro de una celda.
  • 2FN: cada atributo no clave depende de cada clave candidata completa.
  • 3FN: no existen dependencias transitivas entre atributos no clave.
  • La normalización reduce redundancia y anomalías.
  • No garantiza por sí sola consultas más rápidas.

Índices y normalización resuelven problemas diferentes: los índices ayudan a acceder a los datos y la normalización ayuda a organizarlos correctamente.
