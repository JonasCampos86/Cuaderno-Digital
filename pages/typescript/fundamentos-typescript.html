TypeScript: lo que añade a JavaScript

Guía del módulo · Tipos, contratos y herramientas para construir programas sobre una base de JavaScript.

Antes de empezar

TypeScript añade a JavaScript un sistema de tipos estático. Analiza el código antes de ejecutarlo, avisa de posibles errores y después genera JavaScript.

Los tipos ayudan durante el desarrollo, pero normalmente desaparecen al compilar y no validan datos durante la ejecución.

Alcance: estos apuntes cubren el bloque inicial e intermedio estudiado en el módulo. Están pensados como material autónomo de consulta, pero no pretenden incluir todavía todas las funciones avanzadas del lenguaje.

Los ejemplos son independientes y reutilizan algunos nombres. Practícalos por separado; no copies toda la guía en un único archivo TypeScript. Cuando un apartado necesita una definición anterior, se indica en el texto.

Las explicaciones sobre null y undefined presuponen la comprobación estricta de tipos. Utiliza la configuración del proyecto de prácticas para comparar los resultados.

1. Modelo mental de TypeScript

En el flujo de compilación habitual se comprueban los tipos y se genera JavaScript para ejecutarlo. Algunas herramientas permiten ejecutar archivos TypeScript directamente, pero eso no implica que comprueben sus tipos.

Esquema del proceso: 

Código TypeScript → comprobación de tipos → código JavaScript → ejecución

Análisis frente a ejecución

Elemento Durante el análisis Durante la ejecución
interface Comprueba la forma de los valores Desaparece
type Crea aliases y combinaciones de tipos Desaparece
as Modifica la información aceptada por TypeScript No convierte el valor
enum Define miembros tipados Genera un objeto real

// @ts-nocheck desactiva la comprobación del archivo. Si un ejercicio pide encontrar errores de tipos, hay que retirar esa línea.

Comprobar los tipos sin generar JavaScript: 

npx tsc --noEmit

Ejecutar directamente un archivo TypeScript durante las prácticas: 

npx tsx ejercicios-clase-1/inicio.ts

tsx ejecuta el código sin comprobar los tipos. Utiliza también npx tsc --noEmit en el proyecto de prácticas. Estos comandos presuponen que sus herramientas están instaladas en ese proyecto.

La carpeta del proyecto y tsconfig.json

tsconfig.json contiene las reglas con las que TypeScript analiza el proyecto. Opciones como strict o noUncheckedIndexedAccess pueden cambiar los avisos que aparecen.

Conviene abrir en VS Code la carpeta completa del proyecto, no solamente un archivo suelto. De lo contrario, el editor puede no localizar su tsconfig.json y mostrar comprobaciones diferentes.

npx tsc --noEmit debe ejecutarse desde la carpeta del proyecto que contiene —o queda incluida por— el tsconfig.json correspondiente.

2. Anotaciones e inferencia

Una anotación indica explícitamente qué tipo admite una variable. La inferencia permite que TypeScript lo deduzca a partir del valor. 

let disponible: boolean = true; // anotación explícita
let cantidad = 5;               // TypeScript infiere number
let nombre: string = "Juan";

Arrays y tuplas

let numeros: number[] = [1, 2, 3];
let otrosNumeros: Array<number> = [4, 5, 6];

let coordenada: [number, string] = [1, "norte"];

number[] y Array<number> representan un array de números.

[number, string] es una tupla: cada posición tiene un tipo determinado y la longitud está controlada.

Propiedades opcionales

interface Producto {
  id: number;
  nombre: string;
  descripcion?: string;
}

El símbolo ? indica que la propiedad puede no existir. Cuando intentamos leerla, su tipo es string | undefined.

Funciones

function calcularTotal(precio: number, unidades: number): number {
  return precio * unidades;
}

const saludar = (nombre: string): string => `Hola, ${nombre}`;

En una función se pueden tipar por separado los parámetros que entran y el valor que devuelve.

3. Tipos especiales

Tipo Uso Precaución
any Desactiva prácticamente la comprobación Oculta errores futuros
unknown Representa un valor cuyo tipo todavía no conocemos Hay que comprobarlo antes de usarlo
void La función no entrega un valor útil No significa que una función async deje de devolver una promesa
never Algo que no puede suceder o una función que nunca termina normalmente No es el texto "never"
null Ausencia intencionada de valor Es un valor real de JavaScript
undefined Valor no definido Puede aparecer al acceder a datos inexistentes

any frente a unknown

let datoAny: any = "hola";
datoAny.metodoQueNoExiste(); // TypeScript no avisa

let datoUnknown: unknown = "hola";
// datoUnknown.toUpperCase(); // Error: todavía no está comprobado

if (typeof datoUnknown === "string") {
  datoUnknown.toUpperCase(); // Permitido
}

unknown obliga a demostrar qué tipo contiene; any evita que TypeScript haga su trabajo.

void

function mostrarMensaje(mensaje: string): void {
  console.log(mensaje);
}

async function cargarDatos(): Promise<void> {
  console.log("Cargando...");
}

Una función async siempre devuelve una promesa. Promise<void> significa que esa promesa no entregará un valor útil.

never

function lanzarError(mensaje: string): never {
  throw new Error(mensaje);
}

4. Interfaces, type aliases y shapes

Interfaces

interface Producto {
  id: number;
  nombre: string;
  precio: number;
  disponible: boolean;
  descripcion?: string;
}

const teclado: Producto = {
  id: 1,
  nombre: "Teclado mecánico",
  precio: 149.99,
  disponible: true,
};

Una interfaz describe la forma que debe tener un valor.

La interfaz no crea el objeto, no transforma sus propiedades y no existe durante la ejecución.

Type aliases y tipos literales

type Rol = "admin" | "lector";
type EstadoPeticion = "cargando" | "exito" | "error";

let estado: EstadoPeticion = "cargando";
// estado = "terminado"; // Error

TypeScript permite crear tipos propios para representar las reglas del programa, no solo usar string, number o boolean.

interface frente a type

Necesidad Opción habitual
Describir la estructura de un objeto o una clase interface
Crear una unión de valores type
Crear una tupla o un alias para otro tipo type
Ampliar una estructura interface A extends B o una intersección con &

Ambos pueden describir objetos. No es necesario convertir la elección en una regla absoluta: lo importante es utilizar cada herramienta de forma coherente.

Shapes y tipado estructural

TypeScript comprueba la forma del valor: qué propiedades y métodos contiene. No necesita que proceda de una clase concreta. 

interface PersonaInterface {
  nombre: string;
  getNombre: () => string;
  setNombre: (nombre: string) => void;
}

class Persona {
  nombre: string;

  constructor(nombre: string) {
    this.nombre = nombre;
  }

  getNombre(): string {
    return this.nombre;
  }

  setNombre(nombre: string): void {
    this.nombre = nombre;
  }
}

const recibirPersona = (persona: PersonaInterface): void => {
  console.log(persona.getNombre());
};

recibirPersona(new Persona("Gentleman"));

recibirPersona({
  nombre: "Gentleman",
  getNombre: () => "Gentleman",
  setNombre: (nombre: string) => console.log(nombre),
});

La instancia y el objeto literal son compatibles porque ambos cumplen la misma shape.

En el tipado estructural importa qué contiene un valor, no de dónde procede.

5. Union e intersection

interface Alumno {
  nombre: string;
  nota: number;
}

interface Profesor {
  nombre: string;
  legajo: number;
}

Union: |

type AlumnoOProfesor = Alumno | Profesor;

El valor puede ser un Alumno o un Profesor. Sin comprobar cuál ha llegado, solamente podemos utilizar directamente las propiedades comunes. 

function mostrarEntidad(entidad: AlumnoOProfesor): void {
  console.log(entidad.nombre); // Existe en ambos

  if ("nota" in entidad) {
    console.log(entidad.nota); // Alumno
  } else {
    console.log(entidad.legajo); // Profesor
  }
}

Una unión no mezcla automáticamente las propiedades: representa distintas posibilidades.

Intersection: &

type AlumnoYProfesor = Alumno & Profesor;

const ayudante: AlumnoYProfesor = {
  nombre: "Ana",
  nota: 9,
  legajo: 42,
};

El valor debe cumplir simultáneamente los dos contratos.

Una unión representa posibilidades; una intersección acumula requisitos.

6. Narrowing y type guards

Narrowing es el proceso por el que TypeScript reduce un tipo amplio después de una comprobación.

Narrowing con typeof

function procesarEntrada(entrada: string | number | boolean): string {
  if (typeof entrada === "string") {
    return entrada.toUpperCase();
  }

  if (typeof entrada === "boolean") {
    return entrada ? "Sí" : "No";
  }

  return entrada.toFixed(2); // Aquí solamente puede ser number
}

La comprobación correcta es typeof entrada === "string". Comparar entrada === "string" pregunta si el valor contiene literalmente ese texto.

Accesos mediante índices

const valores = [
  { numero: 1, label: "número 1" },
  { numero: 2 },
];

const indices = [1, 2];

indices.forEach((index) => {
  const value = valores[index];

  if (value?.label) {
    console.log(value.label);
  }
});

Guardar el acceso en una variable estable y comprobarlo con ?. permite que TypeScript conserve el narrowing.

El índice 2 no existe en un array de dos elementos: sus índices válidos son 0 y 1. La comprobación también evita un fallo real durante la ejecución.

Para que TypeScript añada undefined al tipo de un acceso como valores[index], el proyecto debe tener activada la opción noUncheckedIndexedAccess en su tsconfig.json. Aunque no esté activada, el riesgo durante la ejecución sigue existiendo.

value?.label comprueba que value exista y que label sea un valor verdadero. Si una cadena vacía también fuese válida, convendría comprobar value?.label !== undefined.

Type guard personalizado

interface UsuarioAPI {
  id: number;
  name: string;
  email: string;
}

function esArrayDeUsuarioAPI(x: unknown): x is UsuarioAPI[] {
  if (!Array.isArray(x)) return false;

  return x.every((item) => {
    if (typeof item !== "object" || item === null) return false;

    const obj = item as Record<string, unknown>;

    return (
      typeof obj["id"] === "number" &&
      typeof obj["name"] === "string" &&
      typeof obj["email"] === "string"
    );
  });
}

Array.isArray(x) solo demuestra que x es un array; no demuestra qué contienen sus elementos. Esa es la razón por la que después se utiliza every().

Un array vacío supera every() porque no contiene ningún elemento inválido. Si la aplicación exigiera al menos un usuario, habría que comprobar también x.length > 0.

Durante la ejecución esta función devuelve un booleano.

x is UsuarioAPI[] informa a TypeScript de que, cuando el resultado sea true, puede tratar x como UsuarioAPI[].

El predicado no convierte ni modifica físicamente el valor.

TypeScript confía en lo que afirma un type guard personalizado. Si la función devuelve true sin haber validado correctamente los datos, el compilador creerá una información falsa.

Aserciones con as

const obj = item as Record<string, unknown>;

Esta aserción permite consultar las propiedades para realizar las comprobaciones posteriores.

as no valida, no transforma y no garantiza que nuestra afirmación sea verdadera durante la ejecución.

7. Datos externos: unknown, validación y modelo interno

Este apartado reutiliza UsuarioAPI y esArrayDeUsuarioAPI del apartado 6.

Una respuesta externa puede contener cualquier cosa. Tiparla directamente como nuestro modelo sería confiar sin comprobar. 

type Rol = "admin" | "lector";

interface Usuario {
  id: number;
  nombre: string;
  email: string;
  rol: Rol;
}

Mapper

function mapearUsuario(u: UsuarioAPI, indice: number): Usuario {
  return {
    id: u.id,
    nombre: u.name,
    email: u.email,
    rol: indice === 0 ? "admin" : "lector",
  };
}

El mapper recibe un modelo y devuelve otro objeto con la forma del modelo interno.

Asignar el rol por la posición del array es una regla del ejercicio. Los permisos reales deben decidirse y comprobarse en el servidor.

Filtro tipado

function filtrarPorRol(usuarios: Usuario[], rol: Rol): Usuario[] {
  return usuarios.filter((u) => u.rol === rol);
}

Recibe un array de usuarios y un rol permitido. Devuelve un nuevo array de usuarios.

filter() crea un array nuevo, pero conserva las referencias a los mismos objetos que superan el filtro.

Proceso completo

async function cargarYFiltrar(): Promise<void> {
  let usuarios: Usuario[];

  try {
    const res = await fetch("https://jsonplaceholder.typicode.com/users");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);

    const crudo: unknown = await res.json();

    if (!esArrayDeUsuarioAPI(crudo)) {
      throw new Error("La respuesta no contiene usuarios válidos");
    }

    usuarios = crudo.map(mapearUsuario);

    const administradores = filtrarPorRol(usuarios, "admin");
    const lectores = filtrarPorRol(usuarios, "lector");

    console.log(administradores, lectores);
  } catch (error: unknown) {
    const mensaje =
      error instanceof Error ? error.message : "Error desconocido";

    console.error(mensaje);
  }
}

Flujo de los datos: 

JSON externo       Type guard          Mapper
unknown       →    UsuarioAPI[]    →   Usuario[]

El type guard valida; el mapper transforma. Son responsabilidades diferentes.

8. Enums

Un enum agrupa un conjunto cerrado de valores con nombres reconocibles.

A diferencia de la mayoría de construcciones de tipos, un enum genera código JavaScript y existe durante la ejecución.

Enum numérico

enum Color {
  RED,
  GREEN,
  BLUE,
}

Color.RED; // 0
Color.GREEN; // 1
Color.BLUE; // 2
Color[0]; // "RED"

Si no se especifican números, empiezan en 0 y se incrementan automáticamente.

Los enums numéricos generan mapeo directo e inverso: 

RED → 0
0   → RED

De forma aproximada, durante la ejecución existe un objeto con las dos direcciones: 

{
  0: "RED",
  1: "GREEN",
  2: "BLUE",
  RED: 0,
  GREEN: 1,
  BLUE: 2,
}

Enum de texto

enum ColorTexto {
  RED = "red",
  GREEN = "green",
  BLUE = "blue",
}

ColorTexto.RED; // "red"

Los enums de texto no generan el mapeo inverso de valor a nombre.

Enum frente a unión literal

enum ColorEnum {
  RED = "red",
  GREEN = "green",
}

type ColorUnion = "red" | "green";
Opción Uso Ejecución
Enum ColorEnum.RED Existe como objeto real
Unión literal const color: ColorUnion = "red" El alias desaparece

Alternativa con un objeto as const

const Colores = {
  RED: "red",
  GREEN: "green",
} as const;

type Color = (typeof Colores)[keyof typeof Colores];
// "red" | "green"

keyof typeof Colores obtiene la unión de sus claves y el acceso indexado obtiene los tipos de sus valores.

Esta alternativa crea un objeto JavaScript normal y deriva de él una unión literal. No significa que los enums sean incorrectos; son dos herramientas con resultados de ejecución distintos.

Excepción avanzada: un const enum puede eliminarse al compilar e insertar sus valores directamente. Estos apuntes utilizan enums normales, que sí generan un objeto.

9. Genéricos

Un genérico representa un tipo que todavía no conocemos y mantiene relaciones entre varias partes del contrato sin recurrir a any.

Función genérica

const identidad = <T>(valor: T): T => valor;

const texto = identidad("hola");      // T se infiere como el literal "hola"
const numero = identidad<number>(42); // T es number

// identidad<number>("hola");
// Error: se prometió que T sería number

El mismo T relaciona el tipo del argumento con el tipo del retorno: entra un tipo y sale ese mismo tipo.

Interface genérica

interface Pais<T> {
  nombre: string;
  nip: T;
}

const argentina: Pais<number> = {
  nombre: "Argentina",
  nip: 1234,
};

const espana: Pais<string> = {
  nombre: "España",
  nip: "ES-28001",
};

Al utilizar Pais<number>, todas las apariciones de T dentro del contrato se interpretan como number.

10. Sobrecarga de funciones

La sobrecarga describe varias formas válidas de llamar a una misma función y relaciona cada entrada con un retorno preciso.

Ejemplo básico

// Firmas de sobrecarga
function convertir(param: string): number;
function convertir(param: number): string;

// Única implementación real
function convertir(param: string | number): string | number {
  if (typeof param === "string") {
    return param.length;
  }

  return param.toString();
}

const longitud = convertir("hello"); // number
const texto = convertir(25);         // string

Sobrecarga con modelos diferentes

interface AlumnoCompleto {
  id: number;
  nombre: string;
  apellidos: string;
  nota: number;
}

interface ProfesorCompleto {
  id: number;
  nombre: string;
  apellidos: string;
  legajo: number;
}

function obtenerDato(param: AlumnoCompleto): number;
function obtenerDato(param: ProfesorCompleto): string;

function obtenerDato(
  param: AlumnoCompleto | ProfesorCompleto
): string | number {
  if ("nota" in param) return param.nota;
  return param.nombre;
}

const alumno: AlumnoCompleto = {
  id: 1,
  nombre: "Luis",
  apellidos: "Pérez",
  nota: 8,
};

const nota = obtenerDato(alumno); // TypeScript sabe que es number

Las sobrecargas son contratos alternativos, pero solo existe una implementación durante la ejecución.

La firma de implementación debe ser compatible con todas las sobrecargas. No se utiliza como una firma adicional desde fuera.

11. Tipos derivados: typeof y ReturnType

typeof en una posición de tipo

const calificacion = {
  a: 1,
  b: 2,
  nota: 4,
  setNota(n: number) {
    this.nota = n;
  },
};

type Parametro = typeof calificacion;

const sumar = (param: Parametro): number =>
  param.a + param.b + param.nota;

En una posición de tipo, typeof obtiene el tipo que TypeScript ha inferido para una variable.

No es la operación de JavaScript que devuelve textos como "object" o "string".

ReturnType

const crearCalificacion = () => ({
    a: 1,
    b: 2,
    nota: 4,
    setNota(n: number) {
      this.nota = n;
    },
    getNota() {
      return this.nota;
    },
});

type CalificacionCreada = ReturnType<typeof crearCalificacion>;

function utilizarCalificacion(param: CalificacionCreada): number {
  param.setNota(8);
  return param.getNota();
}

typeof obtiene el tipo de la función; ReturnType extrae el tipo que devuelve esa función.

Si se aplica ReturnType a una función sobrecargada, TypeScript toma el retorno de la última firma disponible; no genera automáticamente una unión de todos los retornos.

12. Utility types o tipos de utilidad

Los utility types reciben un tipo y producen otro. Evitan copiar contratos para realizar pequeñas variaciones. 

interface Usuario {
  nombre: string;
  apellidos: string;
  edad: number;
}

Utilidades sobre propiedades

Utility type Transformación Ejemplo
Partial<T> Convierte todas las propiedades en opcionales Partial<Usuario>
Required<T> Convierte todas las propiedades en obligatorias Required<Partial<Usuario>>
Readonly<T> Impide reasignar las propiedades mediante TypeScript Readonly<Usuario>
Pick<T, K> Conserva únicamente las claves seleccionadas Pick<Usuario, "nombre" | "apellidos">
Omit<T, K> Elimina las claves seleccionadas Omit<Usuario, "edad">
Record<K, V> Crea un objeto con claves K y valores V Record<string, string | number> 
type UsuarioOpcional = Partial<Usuario>;
type UsuarioObligatorio = Required<UsuarioOpcional>;
type UsuarioSoloLectura = Readonly<UsuarioObligatorio>;
type NombreCompleto = Pick<Usuario, "nombre" | "apellidos">;
type UsuarioSinEdad = Omit<Usuario, "edad">;

Record y la corrección del ejemplo de clase

Record<K, V> resulta especialmente útil para representar diccionarios: objetos cuyas claves siguen un patrón y cuyos valores comparten un tipo. 

const notas: Record<string, number> = {
  Ana: 9,
  Luis: 7,
};

El ejemplo de clase era incorrecto porque Record<string, string> exige que todos los valores sean string, pero edad: 25 contiene un number.

Esta sería su corrección mínima: 

type RegistroMixto = Record<string, string | number>;

const registroMixto: RegistroMixto = {
  nombre: "Juan",
  apellidos: "Pérez",
  edad: 25,
};

Aunque RegistroMixto compila, es demasiado permisivo para representar un usuario: admite cualquier clave y permite que todas las propiedades sean string o number.

Cuando conocemos las propiedades y cada una tiene un significado diferente, una interface conserva un contrato más preciso. 

interface UsuarioPreciso {
  nombre: string;
  apellidos: string;
  edad: number;
}

Utilidades sobre uniones

Este ejemplo usa la interfaz Usuario de este apartado y la interfaz Alumno del apartado 5. 

type Persona = Usuario | Alumno;

type SoloAlumno = Exclude<Persona, Usuario>;
type SoloUsuario = Extract<Persona, Usuario>;

type Complejo = string | number | boolean | null | undefined;
type Definido = NonNullable<Complejo>;
// string | number | boolean
Utility type Resultado
Exclude<A | B, A> Elimina de la unión los miembros compatibles con A
Extract<A | B, A> Conserva los miembros compatibles con A
NonNullable<T> Elimina null y undefined

Readonly<T> es superficial y pertenece al sistema de tipos. No sustituye a Object.freeze() ni congela físicamente el objeto.

13. Const assertions: as const

as const pide a TypeScript que conserve los valores literales más concretos y marque la estructura como de solo lectura. 

const configuracion = {
  modo: "oscuro",
  intentos: 3,
} as const;

// Tipo inferido:
// {
//   readonly modo: "oscuro";
//   readonly intentos: 3;
// }

const numeros = [1, 2, 3] as const;
// readonly [1, 2, 3]

const frente a as const

Código Qué impide Qué infiere
const objeto = { modo: "oscuro" } Reasignar la variable modo suele ampliarse a string
{ modo: "oscuro" } as const También marca la propiedad como readonly Conserva el literal "oscuro"

as const no congela el valor durante la ejecución. Es una const assertion, no una llamada a Object.freeze().

14. Indexed access, mapped types y combinación de enums

enum Keys {
  A = "a",
  B = "b",
}

enum Keys2 {
  C = "c",
  D = "d",
}

const myKeys = { ...Keys, ...Keys2 };
const keyValues = Object.values(myKeys);

type AllKeys = (typeof keyValues)[number];

type CustomType = {
  [key in AllKeys]: string;
};

const customValue: CustomType = {
  a: "valor de a",
  b: "valor de b",
  c: "valor de c",
  d: "valor de d",
};

Proceso paso a paso

  1. { ...Keys, ...Keys2 } combina los dos objetos que existen durante la ejecución.
  2. Object.values(myKeys) obtiene un array con sus valores.
  3. typeof keyValues obtiene el tipo de ese array.
  4. [number] extrae la unión de los tipos que pueden aparecer en cualquier posición.
  5. [key in AllKeys] recorre esa unión y exige una propiedad por cada clave.

T[number] significa «el tipo de los elementos de este array», no «el elemento que ocupa una posición concreta».

La construcción [K in Union] es un mapped type: genera propiedades recorriendo una unión de claves.

Aquí no se fusionan declaraciones de enum. Se combinan sus objetos con spread y después se deriva un tipo a partir del resultado.

Si solo necesitamos combinar los tipos

type AllKeysDirecto = Keys | Keys2;

La unión directa es suficiente cuando solo necesitamos el tipo. El proceso con spread y Object.values() tiene sentido cuando también necesitamos disponer del objeto combinado durante la ejecución.

15. Errores frecuentes y cómo razonarlos

Situación Error conceptual Pregunta útil
entrada === "string" Se compara el valor con un texto ¿Quiero comparar el valor o averiguar su tipo?
Retorno string en una función que usa filter() Se confunde el contenido con el tipo del resultado ¿Devuelve un texto o un array?
Usuario frente a Usuario[] Se confunde un elemento con una colección ¿Tengo un usuario o varios?
crudo.map(...) crudo continúa siendo unknown ¿Qué comprobación demuestra que es un array válido?
x as Usuario Se confunde una aserción con una validación ¿Qué código ha comprobado realmente sus propiedades?
Readonly<T> Se interpreta como protección física ¿Quiero ayuda del compilador o impedir cambios en ejecución?
Promise<void> Se piensa que no se devuelve nada ¿Es async? Entonces devuelve siempre una promesa

Un mensaje de TypeScript no significa automáticamente que la solución sea escribir as. Primero hay que comprobar si ha descubierto un fallo real de lógica, como un índice inexistente o un dato externo sin validar.

Método para investigar cualquier duda

  1. Identifica el valor: ¿qué contiene realmente durante la ejecución?
  2. Lee su tipo actual: coloca el cursor sobre la variable en VS Code o anótalo mentalmente.
  3. Lee el tipo esperado: ¿qué exige la función, propiedad o retorno?
  4. Localiza la diferencia: elemento frente a array, propiedad opcional, unión sin estrechar, dato externo, etc.
  5. Elige la operación correcta: validar, estrechar, transformar o corregir el contrato. Usa as únicamente cuando poseas información real que TypeScript no puede deducir.
  6. Comprueba ambos mundos: ejecuta npx tsc --noEmit para los tipos y después prueba el comportamiento durante la ejecución.

Pregunta decisiva: «¿mi código ha demostrado esto o solamente se lo he afirmado a TypeScript?»

16. Resumen final

TypeScript no cambia lo que JavaScript sabe hacer durante la ejecución: añade información y comprobaciones para construir el programa con contratos más precisos.

Necesidad Herramienta
Describir la forma de un objeto interface o type
Limitar valores concretos "admin" | "lector"
Aceptar distintas posibilidades A | B
Exigir varios contratos simultáneamente A & B
Reducir un tipo amplio typeof, in, Array.isArray, type guards
Trabajar con datos aún no validados unknown
Relacionar tipos sin perder información Genéricos <T>
Relacionar distintas entradas y retornos Sobrecargas
Derivar un tipo desde código existente typeof, ReturnType, acceso indexado
Transformar contratos existentes Partial, Pick, Omit y otros utilities
Conservar literales y readonly as const
Generar propiedades desde una unión Mapped type [K in Union]

Regla práctica: cuando TypeScript no permita una operación, identifica primero el tipo actual, después el tipo que necesitas y, por último, qué comprobación o transformación demuestra el cambio.
